# AI Review для GitHub pull requests

GitHub Actions запускает Kotlin CLI по метке **ai-review**. Reviewer сверяет текст diff с закреплёнными Git blobs, отправляет один запрос в OpenAI и публикует комментарий со ссылками на конкретные строки. Он ищет введённые изменениями существенные дефекты в бизнес-логике, обратной совместимости, конкурентности, соблюдении контрактов и обработке ошибок.

## Подготовка репозитория

1. Опубликуйте workflow, исходники CLI, доверенный prompt, файлы Gradle и Wrapper в защищённой доверенной ветке репозитория. Для первичной настройки опубликуйте workflow в default branch. Проверьте правила Actions организации и репозитория для события `pull_request_target` и доступность GitHub-hosted runner.
2. Создайте метку `ai-review`. Для запуска её ставит пользователь с эффективным GitHub permission `write` или `admin` на открытый PR, который вышел из draft.
3. В настройках **Secrets and variables → Actions** сохраните `OPENAI_API_KEY` как repository secret с ключом API-проекта организации. Установите repository variable `LLM_MODEL` в `gpt-5.4-2026-03-05`. `GITHUB_TOKEN` выдаёт сам GitHub.
4. Выполните проверки приёмки ниже в подготовленном репозитории. Профиль OpenAI и smoke-проверки GitHub нужны перед production rollout.

Событие `pull_request_target` обрабатывается только при установке метки. Workflow делает checkout `github.workflow_sha` в `reviewer` с `persist-credentials: false`, собирает CLI через Gradle Wrapper и передаёт переменные с ключами только шагу запуска. Файлы PR поступают в reviewer как данные через Compare и Git Data API. Тесты кода PR запускаются в отдельном непривилегированном CI. GitHub объявил применение default block с 2 декабря 2026 года для затронутых публичных репозиториев со старой политикой по умолчанию. Проверьте policy insights. Workflow использует доверенный SHA и сохраняет защиту checkout. [Безопасность pull_request_target](https://docs.github.com/en/actions/reference/security/securely-using-pull_request_target)

Для повторной проверки снимите и снова поставьте `ai-review`. Push сам по себе не запускает ревью. Ручной Re-run игнорируется. Для одного PR один job выполняется, а следующие ждут в группе `ai-review-pr-<номер>`. GitHub поддерживает до 100 ожидающих jobs в `queue: max` и отменяет новые при переполнении. Текущий job сохраняется, разные PR могут проверяться параллельно. [Concurrency в GitHub Actions](https://docs.github.com/en/actions/how-tos/write-workflows/choose-when-workflows-run/control-workflow-concurrency)

## Что проверяется

Комментарий указывает `source=COMPARE` и закреплённые base, head и merge-base SHA. Patches и merge-base получены одним ответом Compare. Состав Compare может отличаться от diff, который сейчас показывает интерфейс PR. Reviewer сверяет все строки OLD и NEW из patches с исходным текстом на соответствующих коммитах. Модель получает только пронумерованные patches. Для ссылок используются upstream-репозиторий, старый путь при переименовании и режим исходного текста для Markdown. Ссылка продолжает указывать на ту же версию при последующем push.

| Ограничение | Значение |
| --- | --- |
| Файлы и подготовленный diff | 50 файлов и 30 000 символов Unicode |
| Декодированный исходный текст | 256 KiB на blob и 2 MiB суммарно |
| HTTP целиком, включая чтение тела | GitHub 15 секунд, OpenAI 60 секунд, не больше остатка CLI budget |
| HTTP response body | 1 MiB |
| CLI и job Actions | 14 минут от запуска CLI и 15 минут от начала job, включая checkout и сборку |
| Результат | До пяти замечаний и комментарий до 12 000 символов Unicode |

Ожидание runner или очереди не входит в 15 минут job. Автоматических HTTP retries нет. После исчерпания общего budget новые запросы прекращаются. При принудительной остановке статус может остаться только в Actions.

| Исход | Код процесса | Что происходит |
| --- | --- | --- |
| IGNORED | 0 | Событие, попытка или права не подходят. Комментарий и запрос модели отсутствуют. |
| SKIPPED | 0 | До вызова модели сработал лимит входных данных или не удалось подтвердить patches. При повторно подтверждённом состоянии возможен фиксированный комментарий. |
| STALE | 0 | Изменились состояние или идентификаторы PR. Комментарий не публикуется. |
| REVIEWED | 0 | Опубликован проверенный результат по указанному снимку. |
| ERROR | 1 | Сбой конфигурации, API, дедлайна, результата или публикации. Фиксированная диагностика возможна при подтверждённых правах, актуальном PR и оставшемся budget. |

## Локальная проверка

Нужна Java 21. Обычные тесты используют fake API и loopback, без API-ключей.

~~~~sh
./gradlew test installDist
actionlint .github/workflows/ai-review.yml
~~~~

Actionlint 1.7.12 ещё помечает `queue: max` как неизвестное поле, хотя GitHub документирует его. Для этой версии используйте точечное исключение одной диагностики. Проверка действительного workflow на платформе остаётся частью приёмки.

~~~~sh
actionlint -ignore '^unexpected key "queue" for "concurrency" section\. expected one of "cancel-in-progress", "group"$' \
  .github/workflows/ai-review.yml
~~~~

## Приёмка профиля OpenAI

Проба запускается вручную вне Actions. Она использует только синтетический код и тот же `OpenAiClient`, prompt, строгую схему и HTTP transport, что и CLI. Перед запуском передайте тестовый ключ API-проекта через переменную окружения `OPENAI_API_KEY`.

~~~~sh
./gradlew testClasses installDist
"$JAVA_HOME/bin/java" -Djdk.httpclient.redirects.retrylimit=1 \
  -cp 'build/classes/kotlin/test:build/resources/main:build/install/ai-reviewer/lib/*' \
  aireviewer.LiveProfileProbe --show-synthetic-findings
~~~~

Проба делает по одному запросу на каждый из восьми сценариев для точного профиля `gpt-5.4-2026-03-05`, `reasoning.effort=none`, `max_output_tokens=6000`. Ожидаются пустые findings для изменений только стиля и для случая с явно показанной валидацией, по одному реалистичному замечанию каждой из пяти категорий в пяти коротких случаях и пять замечаний для Unicode diff около 30 000 символов. Последний случай также проверяет форматирование корректных ссылок. Параметр `--case=<имя>` выбирает один сценарий для отдельной проверки.

Код 0 подтверждает автоматические проверки схемы, координат, файлов, категорий и формирования ссылок. Для семантической приёмки оцените замечания из вывода этого же запуска с `--show-synthetic-findings`. Для каждого замечания подтвердите достижимость предпосылок, конкретную последовательность действий и наблюдаемое последствие.

Сохраните факт completed или отказа, HTTP status, latency, output и reasoning token usage по каждому случаю. Не сохраняйте diff, ключи или необработанный ответ API. При ошибке транспорта, доступа, схемы или неполном ответе проба останавливает оставшиеся вызовы. Провал профиля останавливает rollout. Изменение профиля требует отдельного доверенного изменения и повторной приёмки.

## Приёмка на GitHub

| Проверка | Что подтвердить |
| --- | --- |
| Fork, права и trusted checkout | Fork PR содержит маленький дефект и изменения reviewer, prompt, Wrapper и workflow с безвредным индикатором исполнения. Метку ставит write/admin. Индикатор не срабатывает, появляется один комментарий. |
| Исходный текст и ссылки | Ссылки OLD и NEW открывают нужный текст и выделение на конкретных SHA. Проверьте rename, delete, Kotlin/JSON и Markdown с ?plain=1. |
| Согласованный Compare и гонка | Разведите base и head, затем включите часть истории head в base и снова поставьте метку. OLD текст должен совпасть с закреплённым merge-base. Force-push или retarget во время run дают STALE либо явно обозначенный прежний снимок. |
| Очередь и таймаут | Второй label того же PR ждёт, первый job продолжается. Другой PR может выполняться параллельно. Проверьте effective timeout 15 минут. Отдельный временный trusted workflow без credentials и модели с таймаутом 1 минута должен остановить sleep 90. После проверки удалите временный workflow. |
| Private fork | Проверьте доступ к исходному тексту под учётной записью участника с индивидуальной ролью `write` по процедуре ниже. |

### Проверка роли в private fork

1. Создайте private fork под учётной записью другого участника. Выдайте проверяющему индивидуальный `write` в upstream. Для зачёта используйте участника без членства в командах, унаследованных прав, доступа к private fork и полномочий owner или admin в upstream.
2. Войдите в GitHub под учётной записью проверяющего. Откройте прямой URL private fork и подтвердите отказ в доступе.
3. В этой же сессии поставьте метку `ai-review`. Откройте из комментария каждую upstream-ссылку OLD и NEW и убедитесь, что виден исходный текст на указанном SHA и выделены нужные строки.

Source API 404 даёт SKIPPED без обращения к модели. Если бот видит source, а участник не может открыть upstream-ссылки и увидеть выделение, остановите rollout для private-репозитория.

## Статус приёмки

- **Локально.** `./gradlew test installDist --offline` прошёл. 113 тестов успешны, включая две offline-проверки пробных fixtures и ссылок. Стандартный actionlint 1.7.12 остановился на `queue: max`. Повтор с точечным исключением этой диагностики прошёл.
- **OpenAI.** Приёмка профиля не пройдена. Первый сценарий `style-only` вернул HTTP 429 за 2 355 мс без доступного usage. Проба завершилась с кодом 1, семь оставшихся сценариев не запускались.
- **GitHub.** Fork, ссылки под нужной ролью, согласованный Compare, очередь и job timeout ожидают выполнения. Для этого нужны публикация доверенного workflow, права записи и подготовленные тестовые участники.
